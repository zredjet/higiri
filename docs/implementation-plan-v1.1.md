# 実装計画(v1.1)

v1.1 の7つの要件を、フェーズ10〜16の7つに分ける。Windows の実機で確かめることが多く、リスクが一番大きい常駐と通知を最初にする。

仕様は `requirements-design.md` の「v1.1の詳細」にある。この計画は、フェーズごとの作業と完了条件だけを書く。フェーズ9(資料の詳細化)で、この計画と、設計書の v1.1 の記述を書いた。

DB のテーブル定義は変えない(マイグレーションは足さない)。新しい値はすべて `settings` のキーに入れ、検索は既存の列を `LIKE` で引く。

## 進め方

**体制(オーケストレーター方式)**

- 作業場所は `v1.1` ブランチ(main から切ったもの)。
- 計画を持つセッション(オーケストレーター)はコードを書かない。フェーズごとにサブセッションを1つ立て、作業はサブセッションが行う。
- サブセッションは同時に1つだけ動かす。フェーズの間で同じファイル(settings、設定画面、コマンド一覧、`bindings.ts`)を触るため。worktree は使わず、同じフォルダで作業する(`node_modules` と Rust のビルドを毎回やり直さないため)。

**サブセッションがすること**

- 最初に `CLAUDE.md`、この計画、設計書の該当する節を読む。
- そのフェーズだけを行う。設計にない判断が要るときは、進める前にオーケストレーターに聞く。
- 終わったら `npm run check` を通し、`v1.1` にコミットする。push はしない。
- フェーズの終わりに、次の3点を報告して止まる。
  - テストと型チェックの結果
  - 利用者に画面で確認してほしい操作の一覧(`npm run dev:sample` で起動して試す手順)
  - 設計書から変えた点
- フェーズで決まったファイルの場所や決めごとは、`CLAUDE.md` に足す。

**オーケストレーターがすること(各フェーズの後)**

1. 差分を読み、`CLAUDE.md` の決めごと(層の分け方、コマンドの3か所、権限、文言)に合っているかを確かめる。
2. `npm run check` を自分でも通す。
3. 直す点があれば、同じサブセッションに頼む。
4. 結果と、確認してほしい操作を利用者に報告して止まる。
5. 利用者の「次へ」で、次のフェーズのサブセッションを立てる。

**そのほか**

- サブセッションからの質問は、この計画と設計書で答えられるものはオーケストレーターが答え、答えられないものは利用者に聞く。
- 次のことは、利用者に確認してから行う。
  - フェーズ10の Windows 確認のための push と、ワークフローの実行
  - main への取り込み
  - 版の番号(`tauri.conf.json` の `version`)を上げること
- 新しい画面と部品(設定のカード、検索ダイアログ、ドラッグ中の表示)はモックがない。Aizome の部品とトークンで既存の画面に合わせて作り、報告のときに見てもらう。

**全フェーズで守ること**

- `npm run check`(型チェック、Vitest、cargo test、clippy)を通す。日報のフィクスチャとの完全一致のテストは、全フェーズで通ったままにする。
- コマンドを足すときは、`specta_builder()`、`build.rs` の `APP_COMMANDS`、`capabilities/default.json` の3か所をそろえ、件数のテスト(`commands/mod.rs`)も直す。v1.1 で足すコマンドは設計書のコマンド一覧にある5つだけ(27個から32個になる)。
- settings のキーは設計書の「settingsのキー」のとおりにする。読めない値は既定値として扱う。
- notification と autostart のプラグインは Rust からだけ使い、画面側には権限を付けない。

## フェーズ10 常駐・自動起動・OS 通知

**Rust**

- 依存を足す。`tauri` の `tray-icon` 機能、`tauri-plugin-notification`、`tauri-plugin-autostart`、Windows だけレジストリを書く crate(`windows-registry` か `winreg`)。
  - 版は導入時点の最新安定版を確かめる。crates.io では 3.0 の alpha が最新に出るが、使うのは 2.x 系。
  - notification プラグインは Rust 1.90 以上が要るので、手元とワークフローの Rust の版も確かめる。
- `domain/notify.rs`(純粋関数)
  - `pending_slot(now_local, times, last_notified_local)`: 今日の時刻のうち、今以前で、まだ通知していない最も遅い1つを返す。
  - `next_wake(now_local, times)`: 次の時刻までの待ち時間を返す。最長10分で区切り、スリープ明けに時計を見直す。DB は読まない。
  - `message(counts)`: 通知の題名と本文を作る。本文は1件以上の区分だけを、区分の順に「・」でつなぐ(0件の区分は出さない)。
- `notifier.rs`: tokio のタスクで、時刻が来たら次の順に動く。
  1. `commands::clock` で時計を読む。
  2. ダッシュボードと同じ集計(`domain::dashboard`)で件数を出す。
  3. 1件以上なら通知する。0件でも、その時刻は済んだものとして `last_notified_at` を保存する。
  - 起きるたびに日付を見て、変わっていたら `backup::run_daily` でその日のバックアップを取る(起動時と同じく1日1個で、7個残す)。
  - 設定が変わったら `tokio::sync::Notify` で起こして、待ち時間を計算し直す。
  - 通知のクリックでウィンドウを出す(`on_action`。入れる版のデスクトップで動くかを確かめる)。動かなければ、クリックでは何もしない(ウィンドウはトレイから開く)。
- `tray.rs`
  - トレイのアイコンとメニュー(「Higiri を開く」「終了」)。Windows は左クリックでも開く。
  - ウィンドウを出すときは `unminimize` → `show` → `set_focus`。
- `lib.rs`
  - `tauri.conf.json` の main ウィンドウを `visible: false` にし、setup で `--autostart` の引数がなければ出す。
  - `CloseRequested` で `close_to_tray` なら閉じずに隠す。値は `AtomicBool` で持ち、設定の保存時に更新する。トレイを作れなかったときは、隠さずに終了する。
  - 初めて隠したときに1回だけ案内の通知を出し、`tray_hint_shown` を保存する。`notify_enabled` がオフでも出す。
  - macOS の `RunEvent::Reopen`(Dock のクリック)でウィンドウを出す。
  - single-instance のコールバックは、`--autostart` つきの2つ目の起動ならウィンドウを出さない。
  - 復元(`restore_backup`)で settings が入れ替わったときも、`#[tauri::command]` の層でタイマーと×ボタンの動きに反映する。
- 復元(`restore_backup`)では、`autostart`、`last_notified_at`、`tray_hint_shown`、`last_reminded_on` を今の値のまま残す。フェーズ15の取り込みも同じ仕組みを使う。
- `autostart.rs`: 配布版の起動時に、`autostart` の値を OS に反映する。
  - 登録には `--autostart` の引数を付ける(macOS は引数を渡せる `MacosLauncher::LaunchAgent` を使う)。
  - ZIP を置き直すと exe の場所が変わるので、毎回登録し直す。
  - 開発ビルドでは何もしない。
  - macOS で App Translocation の場所から動いていたら登録せず、設計書の文のエラーを返す。
- `win_toast.rs`(Windows の配布版だけ): 起動時に `HKCU\Software\Classes\AppUserModelId\com.redjet.higiri` へ表示名とアイコンのパスを書く。アイコンはデータフォルダに PNG で書き出す。
- settings に `notify_enabled`、`notify_times`、`last_notified_at`、`close_to_tray`、`autostart`、`tray_hint_shown` を足す。`update_settings` で時刻を検証する(形式、1〜5個、重複なし)。OS 側への反映(自動起動の登録、タイマーの計算し直し、`AtomicBool` の更新)は `#[tauri::command]` の層で行う。
- `test_notification` のコマンドを足す。`notify_enabled` がオフでも出す。

**画面**

- 設定画面に「通知と常駐」のカードを足す。
  - スイッチ「OSの通知を出す」と、時刻の一覧(足す・消す)
  - ボタン「通知を試す」
  - スイッチ「ウィンドウを閉じてもトレイに残す」
  - スイッチ「PCにログインしたときに起動する」。開発ビルドでは押せないようにし、理由を添える。

**アイコン**

- `scripts/icons.mjs` でトレイ用のアイコンを作る。Windows はカラーの小さな版、macOS はメニューバー用の単色テンプレート画像。

**テスト**

- `domain/notify.rs`
  - 8:59、9:00 ちょうど、9:30 の起動(9:00 の分を1回)
  - 13:00 の起動(12:55 の1回だけ)
  - 日付の変わり目、前日に通知済み
  - 時刻の重複と順不同
  - 本文に0件の区分を出さないこと
- settings の読み書きと、`update_settings` の検証(時刻の形式、1〜5個、重複なし)
- 常駐中に日付をまたぐと、その日のバックアップが1個でき、同じ日には2個目を作らないこと
- 復元のあとも、`autostart`、`last_notified_at`、`tray_hint_shown`、`last_reminded_on` が復元前の値のまま残ること

**実機での確認**

- macOS の開発ビルドでは、通知が「ターミナル」から届く(開発ビルドの仕様)。
- macOS の配布版(ad-hoc 署名)で通知が届くか。
- Windows の ZIP 版で次を確かめる。ビルドは `windows.yml` で作る(push とワークフローの実行は、その時点で利用者に確認してから行う)。ZIP から取り出した exe で試す(`target\release` の中の exe をそのまま動かすと、プラグインは PowerShell の名前で通知する)。
  - トーストが Higiri の名前で届き、クリックでウィンドウが出るか(プラグインがクリックに対応していなければ、何も起きないことを確かめる)。
  - ログインし直したらトレイで起動するか。
  - × で隠れ、トレイの「終了」で終わるか。
- レジストリで通知が出なければ、スタートメニューのショートカット(`IShellLinkW` + `PKEY_AppUserModel_ID`)に切り替える。

完了条件: `domain/notify.rs`、settings、常駐中のバックアップ、復元で残す値のテストが通る。macOS の配布版と Windows の ZIP 版で、決まった時刻に Higiri の名前で通知が届く。× で隠れてトレイから開き直せ、トレイの「終了」で終わる。自動起動をオンにしてログインし直すと、ウィンドウを出さずにトレイだけで起動する。常駐したまま日付をまたぐと、その日のバックアップができる。要件 D-6、D-7、C-1(常駐中のバックアップ)。

## フェーズ11 営業日

**Rust**

- `domain/holidays.rs`: 日本の祝日を規則から計算する。
  - 今の祝日法の規則(2020年以降のもの)で計算する。2019年以前の改正の歴史は入れない。
  - 固定日、ハッピーマンデー、春分・秋分(2020〜2099年で使える式)、振替休日、国民の休日。
  - 2020・2021年の五輪による移動も入れる。
  - 内閣府の祝日一覧(2020〜2027年)と一致することをテストで確かめる。一覧は実装時に内閣府のページで確かめる。
  - 計算するのは2020〜2099年だけ。その外の年は祝日なしとする(土日だけが休み)。
- `domain/calendar.rs` の `WorkCalendar { mode, custom }` に次を持たせる。
  - `is_business_day`
  - `add_business_days`
  - `business_days_in(a, b]`(週の計算と休日の二分探索で、件数に比例しない形)
  - `effective_due(due)`: 営業日の設定のとき、休日の日限を前の営業日に寄せる。
- `domain/urgency.rs`
  - `classify(todo, today, soon_days)` を `classify(todo, today, &rules)` にする。`rules` は `soon_days` と `WorkCalendar` を持つ。判定はこの1か所のまま。
  - 営業日の設定での判定は、設計書の「営業日での日数」のとおりにする。
  - `Assessment` に `business_days: bool` と `due_shifted: bool`(休日のため前倒し)を足す。
- `views.rs`、`dashboard.rs`、`listing.rs`、`gantt.rs`、`report.rs`、`commands/*`、`sample.rs`、`perf.rs` の呼び出しを直す。
  - 一覧の絞り込み「今日まで」は前倒し後の日限で比べる。「7日後まで」は暦日のまま。
  - 日報の「明日の予定」は、営業日の設定なら次の営業日。
  - 日報の行も、営業日の設定では「あとN営業日」「N営業日超過」にし、前倒しなら「休日のため前倒し」と添える。
- 確認日の初期値を Rust 側に移す。`TodoItem.follow_up_default` を足し、`TodoDetail.tsx` の `addDaysYmd(todayYmd(), followUpDays)` を置き換える。
- settings に `day_count` と `custom_holidays` を足す。`update_settings` で独自の休日を検証する(名前は空にできず30字まで、`start <= end`、長さは31日まで)。
- `list_holidays(start, end)` のコマンドを足す。期間は3年までに制限する。

**画面**

- `todoText.ts`、`rowLabel.ts`、`GanttPage.tsx` の「N日超過」の文を直す。営業日の設定では「あと1営業日」「2営業日超過」と出し、前倒しなら「休日のため前倒し」と添える。ダッシュボードの「N日以内」も「N営業日以内」にする。
- 設定画面の「間近とみなす日数」「確認日の初期値」の単位も、営業日の設定では「営業日以内」「営業日後」にする。
- ガントで祝日と独自の休日を網掛けする(`geometry.ts` の `weekendRuns` を、休日の一覧も受け取る形にする)。見出しにはその日の名前を出す。
- 設定画面に「日数の数え方」のカードを足す。
  - 暦日か営業日かのラジオボタン
  - 独自の休日の一覧と、足す・消す操作
  - 今年の祝日の一覧

**テスト**

- 祝日の月曜(2026-11-23)
- GW(2026-05-03 が日曜で、05-06 が振替休日)
- シルバーウィーク(2026-09-21〜23)

- 暦日の設定で、今の結果が何も変わらないこと(既存のテストとフィクスチャがそのまま通る)
- perf に営業日の設定での計測を足す。

完了条件: 暦日の設定で既存のテストとフィクスチャがそのまま通る。上の境界のテストと、内閣府の祝日一覧との照合が通る。サンプルデータを営業日の設定に切り替えると、ダッシュボード・一覧・ガント・日報の日数に「営業日」が付き、ガントで祝日が網掛けされる。要件: 営業日での残り日数計算(概要の「休日の扱い」、未決事項の3点目)。

## フェーズ12 全文検索

**Rust**

- `repo/search.rs`
  - 語を空白(全角の空白も)で分け、すべての語を含む TODO を引く(AND)。
  - 対象の列は、タイトル、メモ、待っている相手、中止の理由、作業ログの本文(`EXISTS`)。
  - `LIKE … ESCAPE` で引く。アーカイブしたプロジェクトも含める。
  - 返すのは最大100件と、全体の件数。
- `domain/search.rs`(純粋関数)
  - 語の分割
  - 前後の文の切り出し。当たった語の前後30字ほどで、改行は空白にする。`[{text, hit}]` の区切りで返す。
  - 並び順。タイトルに当たったものを先にし、その中は更新の新しい順。
  - 作業ログは、当たったものを TODO ごとに3件まで、日付つきで出す。
- `search_todos({ text })` のコマンドを足す。`SearchResult { hits: [{ item: TodoItem, matches: [...] }], total }` を返す。

**画面**

- `src/features/search/SearchDialog.tsx` を作る。
  - 打った語は200ms 待ってから検索する。日本語の変換中は検索しない(`isComposing`)。
  - ↑↓ で選び、Enter で開く。
  - 選んだら、その TODO のプロジェクトのページ(アーカイブ済みなら全体の TODO)に移り、詳細パネルを開く。
  - 100件を超えたら「100件を超えました。語を足して絞ってください。」と出す。
- `shortcuts.ts` に Ctrl+F を、`nav.ts` に「検索」(`search` のアイコン)を足す。ダイアログは App が持つ。「検索」は画面ではないので `routes.ts` の `Route` には足さず、App のサイドナビの選択でダイアログを開く。

**テスト**

- 語の分割、前後の文、並び順の単体テスト
- `repo` はメモリ上の DB で、`%` や `_` を含む語、大文字と小文字、日本語2文字の語を確かめる。
- perf に検索の時間を足す。

**確認**

- Windows の WebView2 が Ctrl+F を自分の検索に使わないか。

完了条件: 上のテストが通り、`npm run test:perf` で検索が0.1秒以内に収まる。画面で Ctrl+F とサイドナビの「検索」からダイアログを開き、2文字の語で引いて、選んだ TODO の詳細パネルが開く。要件 T-7。

## フェーズ14 日報テンプレート

- `domain/report_template.rs` に `ReportTemplate` を作る。
  - `title` は `{日付}` と `{曜日}` を差し込める。既定は `日報 {日付}({曜日})`。
  - `sections` は `[{ kind, heading, enabled, options }]`。
  - 正規化する。足りない節は既定で補い、重複は除き、所感・連絡事項は常に最後に置く。
  - 節ごとに選べる項目は、設計書の「日報テンプレート」の表のとおり。既定はすべて今の出力と同じ。

## フェーズ15 JSON のエクスポートとインポート

- 書き出す形は、設計書の「JSONのエクスポートとインポート」のとおり。
  - 行は列名をキーにし、値は保存されているままにする。`settings` の値と `todo_events.note` は、JSON の値として埋め込む。
  - `schema_version` は適用済みのマイグレーションの最新の番号。読めるのは `format_version` が1のファイルだけ。
- `export_data` のコマンドを足す。保存先のダイアログを Rust 側で開く(既定の名前は `higiri-YYYY-MM-DD.json`)。書き出しは Rust だけで行う。
- `import_data` のコマンドを足す。
  1. 画面で確認してから、Rust 側でファイルを選ぶダイアログを開く。
  2. 形式と版を確かめる(新しい版のファイルは断る)。
  3. 作業用の DB にマイグレーションを当て、行を入れる。外部キーと CHECK 制約で中身を検査する。
  4. `before-restore-<UTC>.db` に今のデータを退避する。
  5. `backup.rs` の `copy_rows`(ATTACH して1トランザクションで入れ替える)で置き換える。
  - `autostart`、`last_notified_at`、`tray_hint_shown`、`last_reminded_on` は、フェーズ10の復元と同じ仕組みで今の値のまま残す。
  - 取り込みで settings が入れ替わるので、復元と同じく `#[tauri::command]` の層でタイマーと×ボタンの動きに反映する。
- 退避の一覧での表示名を「復元・取り込みの前の状態」にする。復元のダイアログと案内の文にある「復元する前の状態」も合わせて直す。
- 画面
  - 設定画面の「データ」のカードに「JSONで書き出す」「JSONから取り込む」を足す。
  - 取り込みの確認ダイアログと、終わったときの案内を出す。
  - 取り込み後は、復元と同じくすべての一覧を取り直す。

**テスト**

- サンプルデータで、書き出し → 空の DB に取り込み → 全テーブルの行が一致する。
- 新しい版の形式、壊れた JSON、制約違反は断り、データが変わらない。
- 退避が作られる。
- 取り込みのあとも、`autostart`、`last_notified_at`、`tray_hint_shown`、`last_reminded_on` が今の値のまま残る。

完了条件: 上のテストが通る。画面で JSON に書き出し、取り込むと、すべての一覧が取り込んだ内容になる。取り込む前の状態が復元の一覧に「復元・取り込みの前の状態」として出て、そこから戻せる。要件 C-2。
