# 実装計画(MVPまで)

MVP(v1.0)を9つのフェーズに分ける。土台(データと判定ロジック)を先に固め、画面は後から載せる。

## 進め方

- フェーズの順に進める。1つ終えるたびに、次の3点を報告して止まる。
  - テストと型チェックの結果
  - 利用者に画面で確認してほしい操作の一覧(`tauri dev` で起動して試す手順)
  - 設計書から変えた点と、次のフェーズの計画
- フェーズごとにコミットする。
- 設計書にない判断が必要になったら、進める前に相談する。

## フェーズ0 準備

- 開発環境を確認する(OS、Rust、Node.js、Tauri 2 の前提条件)。足りないものは入れ方を案内する。前提条件は https://v2.tauri.app/start/prerequisites/ を参照する。
- git を初期化し、Tauri 2 + React + TypeScript + Vite のひな形をこのフォルダ直下に作る(`src/` と `src-tauri/` ができる形)。ひな形の生成ツールは空でないフォルダを受け付けないことがあるので、`CLAUDE.md` と `docs/` を消さない方法で行う。
- ディレクトリを設計書の構成に合わせる。DBファイル、`target/`、`node_modules/` を `.gitignore` に入れる。
- テスト(Rust、Vitest)と型チェックが空の状態で通るようにし、コマンドを `CLAUDE.md` の「コマンド」に書く。

完了条件: `tauri dev` で空のウィンドウが開く。テストと型チェックのコマンドが通る。

## フェーズ1 データと判定ロジック(Rustのみ)

- `migrations/0001_init.sql` に設計書のDDLをそのまま入れる。
- DBの初期化: アプリのデータフォルダに `todo.db` を作り、マイグレーションを当て、外部キー制約とWALモードを有効にする。
- `domain/urgency.rs`: `classify(todo, today, soon_days)` と、警告2種(計画が間に合わない、予定超過)。
- `domain/status.rs`: 遷移表(行き先ごとの自動入力、完了と中止の直接の行き来は拒否、待ちと中止の必須入力)。
- `repo/`: プロジェクト、TODO、作業ログ、変更履歴、設定の読み書き。

テストで押さえること:

- 区分の境界: 日限が昨日・今日・明日・N日後ちょうど・N+1日後、月またぎ、年またぎ。
- 区分の優先順: 超過 → 本日 → 間近 → 要確認 → 着手遅れ。待ちで日限が間近なら「間近」。完了と中止は対象外。保留は対象(未決事項の仮定)。
- 遷移表の全行。完了からの再開、中止から未着手への戻し、待ちから抜けたときに待ちの3項目が空になること。
- `repo/`: 制約違反(予定開始 > 予定終了、不正なステータス)がエラーになること。プロジェクト削除で配下が消えること。

完了条件: `cargo test` がすべて通る。対応する要件は T-1〜T-3、T-8、T-9、M-5(記録側)。

## フェーズ2 コマンドと型の共有

- `commands/`: プロジェクト、TODO、`change_status`、タイムライン、作業ログ、設定。入力の検証とトランザクションだけを持ち、処理は `domain/` と `repo/` に任せる。
- エラーは画面に返せる型にまとめる。利用者に見せる文は日本語で、「何が起きたか+どうすればよいか」。
- tauri-specta で `src/lib/bindings.ts` を生成する。
- 開発用のサンプルデータ投入を用意する(デバッグビルドのみ)。内容は `ui-mock/README.md` のサンプルデータで、今日からの相対日付にする。
- `capabilities/default.json` を必要な権限だけにする。

完了条件: 画面側から型つきで `list_projects` と `list_todos` を呼び、サンプルデータが返る。

## フェーズ3 画面の土台

- Aizome を移植する。`tokens.css` と `bundle.css`(Google Fonts の `@import` は外す)をスタイルとして読み込み、14部品を TypeScript のコンポーネントにする。フォントを同梱する。
- 共通レイアウト: サイドナビ、コンテンツ、右の詳細パネルの枠。画面の切り替え。ライト/ダークの切り替え(`data-theme`)。
- データ取得は TanStack Query。更新後に関係する一覧を取り直す。
- プロジェクトの作成・編集・アーカイブ・削除(削除は確認つき)。サイドナビに件数バッジ。

完了条件: モックと同じ骨格で6画面の空のページを行き来できる。プロジェクトを作って名前を変えられる。要件 P-1〜P-3。

## フェーズ4 TODO一覧と詳細パネル

- 一覧: ステータス別のタブと件数、クイック追加、絞り込みと並べ替え、行から詳細を開く。
- ステータス変更: 待ちにするときは相手と確認日、中止にするときは理由を入力させる。
- 詳細パネル: 項目の編集、予定終了が日限より後のときの警告、メモ(CodeMirror 6、編集とプレビューの切り替え、1秒後の自動保存)、作業ログの追加、作業ログと変更履歴を混ぜたタイムライン。
- Markdown の表示は react-markdown + remark-gfm + rehype-sanitize。リンクは既定ブラウザで開く。

完了条件: `screenshots/3-todos-*.png` と同じ見た目で、TODOの登録から完了・中止までを画面だけで操作できる。要件 T-1〜T-6、T-8、T-9、M-1〜M-5。

## フェーズ5 ダッシュボード、リマインド、設定

- `get_dashboard`: 日限注意の5区分、今日の作業、待ち、プロジェクト別の進捗。
- ダッシュボードの日限注意から、完了にする、日限や確認日を変える、待ちから作業に戻す、詳細を開く。
- 起動時リマインド: `get_startup_reminder` と `ack_reminder`。頻度の設定(起動のたび / 1日1回)。0件なら出さない。ウィンドウが前面に来たときに日付の変化を調べ、変わっていたら起動時と同じ扱いにする。
- 設定画面: リマインドの頻度、間近の日数、確認日の初期値、配色。

完了条件: サンプルデータで、ダッシュボードとリマインドがモックと同じ5件を同じ区分で出す。頻度を切り替えると挙動が変わる。要件 D-1〜D-5、D-8。

## フェーズ6 ガントチャート

- `get_gantt`: 表示期間とプロジェクトを受け、行データ(予定、実績、待ちの区間、日限、区分)を返す。待ちの区間は `todo_events` から求める。
- SVG で描く。日付から座標への変換は純粋関数にして Vitest でテストする。
- 日・週・月の切り替え、今日の縦線、土日の背景、完了と中止の表示切り替え、バーから詳細を開く。画面に見えている行だけを描く。

完了条件: サンプルデータで `screenshots/4-gantt-*.png` と同じ並びと形になる。要件 G-1〜G-5、G-7。

## フェーズ7 日報

- `domain/report.rs`: 対象日を受け取り、6つの節を組み立てる。
- テスト: 設計書の出力例を再現するフィクスチャ(対象日 2026-11-19、作業ログの本文と作業時間を含む)を作り、出力が一致することを確かめる。
- 画面: 日付の選択と前後移動、再生成、編集、所感・連絡事項(再生成しても消えない)、コピー、保存、.md への書き出し。

完了条件: 上のテストが通る。画面で日報を生成し、所感を書いて保存し、日付から呼び出せる。要件 R-1〜R-4。

## フェーズ8 仕上げ

- バックアップ: その日最初の起動時に1回、7日分を残す。設定画面から一覧と復元。復元の前に現在のDBを退避する。
- 多重起動の防止、ウィンドウの位置と大きさの復元、動作ログ。
- キーボードショートカット(設計書の表)。
- 権限と CSP の見直し。外部への通信がないことの確認。
- 性能の確認: TODO 5,000件・作業ログ 20,000件を投入し、起動からダッシュボード表示までと、一覧・ガントの応答を測る。
- 配布物のビルド(Windows のインストーラー)。

完了条件: 非機能要件の表を1行ずつ確認し、結果を報告する。要件 C-1。
