# 実装計画(v0.3.0)

v0.3.0 の5つの要件(S-1 サブTODO、T-10 TODOテンプレート、T-12 繰り返しTODO、T-11 TODO間の依存関係、R-6 週報)を、フェーズ17〜24に分ける。テンプレートと繰り返しは子TODOを含む一式を扱うので、サブTODOを先に作る。依存関係は、テンプレートと繰り返しで一式の中の依存を写すところまで含めるので、その2つの後にする。週報はほかとつながりがないので最後にする(順番を前にしてもよい)。

仕様は `requirements-design.md` の「v0.3.0の詳細」にある。この計画は、フェーズごとの作業と完了条件だけを書く。フェーズ17(資料の詳細化)で、この計画と、設計書の v0.3.0 の記述を書いた。

v0.3.0 から、段階はアプリの版番号で呼ぶ(「v2」の呼び名はやめた。利用者が決定)。

## 進め方

**体制(オーケストレーター方式)**

v1.1 と同じ。

- 作業場所は `dev-0.3.0` ブランチ(main から切ったもの)。リリースのタグ `v0.3.0` と同じ名前にしない(同じ名前のブランチとタグがあると、git の指定があいまいになるため)。
- 計画を持つセッション(オーケストレーター)はコードを書かない。フェーズごとにサブセッションを1つ立て、作業はサブセッションが行う。
- サブセッションは同時に1つだけ動かす。フェーズの間で同じファイル(`commands/todos.rs`、`domain/views.rs`、詳細パネル、コマンド一覧、`bindings.ts`)を触るため。worktree は使わず、同じフォルダで作業する。

**サブセッションがすること**

- 最初に `CLAUDE.md`、この計画、設計書の該当する節を読む。
- そのフェーズだけを行う。設計にない判断が要るときは、進める前にオーケストレーターに聞く。
- 終わったら `npm run check` を通し、`dev-0.3.0` にコミットする。push はしない。
- フェーズの終わりに、次の3点を報告して止まる。
  - テストと型チェックの結果
  - 利用者に画面で確認してほしい操作の一覧(`npm run dev:sample` で起動して試す手順)
  - 設計書から変えた点
- フェーズで決まったファイルの場所や決めごとは、`CLAUDE.md` の「v0.3.0 の決めごと」に足す。

**オーケストレーターがすること(各フェーズの後)**

1. 差分を読み、`CLAUDE.md` の決めごと(層の分け方、コマンドの3か所、権限、文言)に合っているかを確かめる。
2. `npm run check` を自分でも通す。
3. 直す点があれば、同じサブセッションに頼む。
4. 結果と、確認してほしい操作を利用者に報告して止まる。
5. 利用者の「次へ」で、次のフェーズのサブセッションを立てる。

**そのほか**

- サブセッションからの質問は、この計画と設計書で答えられるものはオーケストレーターが答え、答えられないものは利用者に聞く。
- 次のことは、利用者に確認してから行う。
  - main への取り込み
  - 版の番号(`tauri.conf.json` の `version`)を 0.3.0 に上げること
  - push、タグ、リリース、ワークフローの実行
- 新しい画面と部品(詳細パネルの欄、一覧とガントの木の形、各ダイアログ、設定のカード、日報の画面の切り替え)はモックがない。Aizome の部品とトークンで既存の画面に合わせて作り、報告のときに見てもらう。

**全フェーズで守ること**

- `npm run check`(型チェック、Vitest、cargo test、clippy)を通す。日報のフィクスチャとの完全一致のテストは、全フェーズで通ったままにする。
- コマンドを足すときは、`specta_builder()`、`build.rs` の `APP_COMMANDS`、`capabilities/default.json` の3か所をそろえ、件数のテスト(`commands/mod.rs`)も直す。v0.3.0 で足すコマンドは設計書のコマンド一覧にある9つだけ(32個から41個になる)。フェーズごとの件数は、18で32、19で33、20で37、21で38、22で41、23で41。
- `0002_v0_3_0.sql` はフェーズ18でコミットしたら書き換えない。表を変えたくなったら、新しいマイグレーションを足す前にオーケストレーターに相談する。
- `todo_events.note` のキーと、settings のキーは設計書と `CLAUDE.md` のとおりにする。読めない値は既定値として扱う。
- サンプルデータ(`sample.rs`)に新しい機能のデータを足すときは、モックと見比べる今の11件の表示(ダッシュボードの日限注意の件数と並び)を変えない。
- `perf.rs` の計測のデータに、各フェーズの機能のデータを足す(子TODO、テンプレート、繰り返し、依存関係)。一覧とガントは0.1秒以内のまま。

## フェーズ18 データの土台

表を足し、バックアップ・復元・JSON が新しい表を扱えるようにする(設計書の「表の追加とデータの読み書き」)。画面は変えない。

**Rust**

- `src-tauri/migrations/0002_v0_3_0.sql`: 設計書の DDL のとおり、`todo_templates`、`todo_repeats`、`todo_dependencies` と索引を作る。
- 値の型(`domain/`。計算はそれぞれのフェーズで足す)
  - `domain/template.rs`: `TemplateBody { title, priority, memo_md, children: [TemplateChild { title, priority, memo_md, due_offset_days, depends_on }] }`。serde で設計書の JSON の形にする(`depends_on` がなければ `[]`)。検査(タイトルは必須で、TODO と同じく前後の空白を除いて空でないこと。`depends_on` は範囲内で自分以外の子の位置、重複と循環なし)。
  - `domain/repeat.rs`: `RepeatRule`(`kind` で分ける serde の enum)と、範囲の検査(`weekdays` は1〜7個で重複なし、`day` は1〜31、`week` は1〜4か-1、`month` と `day` は暦にある月日(2/29は可)、`days` は2〜365)。
- `repo/templates.rs`、`repo/repeats.rs`、`repo/dependencies.rs`: 読み書き(一覧、1件、追加、更新、削除)。`body` と `rule` は読むときに型にし、読めない値はエラーにする。
- `backup.rs`: `DELETE_CHILD_FIRST` と `INSERT_PARENT_FIRST` に3つの表を足す(消すのは `todo_dependencies`、`todo_repeats` を `todos` より先、入れるのは `todos` より後)。`todo_templates` はほかの表を指さない。
- `json_data.rs`
  - `TABLES` に `todo_templates`(`body` を JSON の値として埋め込む)、`todo_repeats`(`rule` を同じく埋め込む)、`todo_dependencies` を、`reports` の後に足す。行の順は、`todo_templates` は `id`、`todo_repeats` は `todo_id`、`todo_dependencies` は `todo_id, depends_on_id`。
  - 取り込みで、ファイルの `schema_version` が1(v0.2.0 まで)なら、3つの表のキーがなくてよい(空として扱う)。2以上でキーがなければ `Malformed`。
  - 取り込みの読み直し(「アプリの読み取りで全行を読み直す」)に3つの表を足す。`body` と `rule` が読めなければ `Unreadable`。
- `repo/db.rs` の表の一覧のテストを直す。
- `CLAUDE.md` の「データの決めごと」を直す(表の追加、バックアップと JSON の表の並び)。

**テスト**

- マイグレーションが、新しい DB と、v0.2.0 の DB(`0001` だけを当てた DB に行を入れたもの)の両方に当たり、今の行が変わらない。
- 3つの表の読み書き。`ON DELETE CASCADE`(TODO を消すと周期と依存が消える。プロジェクトを消しても同じ)。依存の主キーの重複と、自分自身への依存の CHECK。
- 周期とテンプレートの JSON の読み書きと検査(範囲の境界)。
- バックアップ: 3つの表を含めて復元で入れ替わる。v0.2.0 の形のバックアップ(`0001` だけの DB)を復元できる(足りない表は空になる)。
- JSON: 3つの表を含めて、書き出し → 空の DB に取り込み → 全表の行が一致する。`schema_version` 1 のファイル(v0.2.0 の書き出しの形)を取り込める。`schema_version` 2 で表のキーがないファイル、読めない `body` と `rule` は断り、データが変わらない。

完了条件: 上のテストが通る。`npm run dev:sample` で起動して今までどおり動き、JSON の書き出しに3つの表(空の配列)が入る。画面での確認はこれだけ。

## フェーズ19 サブTODO

**Rust**

- 親子の検査(純粋関数): 親になれるのは親のないTODO、子になれるのは子のないTODO、同じプロジェクト、自分自身は不可。
- `commands/todos.rs`
  - `NewTodoInput` に `parent_id` を足す。プロジェクトが親と違えば断る。
  - `set_todo_parent(id, parent_id)` を足す(コマンドの3か所と件数のテスト。33個)。
  - `change_status_impl`: 完了・中止にするとき、開いている子を同じトランザクションで同じ状態にする。子ごとに `transition` を通し、変更履歴を1行ずつ残す。中止の理由は親と同じ。
- `domain/views.rs`: `TodoItem` に `parent_title`、`children`(`{ total, done, open }`)、`due_after_parent` を足す。一覧ではまとめて読んだTODOから数え、1件の読み取り(`get_todo` など)では子を引いて数える。
- `domain/listing.rs`: 木の順に並べる関数。絞り込みは1件ずつ判定し、当たった子の親が当たっていなければ、つなぎの行として親を出す。親どうしと、同じ親の子どうしは、選んだ並べ替えで並べる。`TodoList` の行に「子の行か」「つなぎの行か」を持たせ、状態のタブの件数にはつなぎの行を数えない。
- `domain/gantt.rs`: 親の直後に子の行。`GanttRow` に「子の行か」「つなぎの行か」(完了・中止を隠す設定で親だけが隠れるとき、親をバーなしで出す)。
- 表示の名前: `domain/dashboard.rs`(リマインドを含む)、`domain/report.rs`、検索の結果で、子に親のタイトルを添える。日報の行は「プロジェクト / 親 / 子」、本日の作業の太字は「**親 / 子**」。
- 子の日限が親の日限より後のとき(`due_after_parent`)の警告を、一覧とガントの警告アイコンに出す。
- `sample.rs`: 親1件と子3件ほどを足す(今の11件の表示を変えない)。
- `perf.rs`: 5,000件のうち1,000件ほどを子にする。

**画面**

- 詳細パネル(`src/features/todos/detail/`)
  - 「親のTODO」の欄(親を開く、選び直す、外す。子のないTODOは親を選んで子になれる)。候補は同じプロジェクトの親のないTODO(自分を除く)。
  - 「子TODO」の欄(親のないTODOだけ): 子の一覧、進み具合、タイトルを打ってEnterで足す欄(`isComposing` で変換中の Enter を除く)、すべて終わったときの文。
  - 完了・中止にするとき、`children.open` が1以上なら確かめる(設計書の文)。ダッシュボードの「完了にする」も同じ(一覧にはステータスを変える操作がない)。
- 一覧(`TodoTable.tsx`): 木の形、開閉のボタン、「子 2/3」、つなぎの行は薄い文字。折りたたみで描く行を決める部分は純粋関数にして Vitest で確かめ、今の見えている行だけを描く処理(`virtualRows.ts`)と組み合わせる。
- ガント(`GanttPage.tsx`): 子の行の字下げ、親の行の開閉と「子 2/3」。
- 削除の確認に「子TODO N件も削除されます。」。
- 文の組み立ては `todoText.ts` などに置き、Vitest で確かめる。

**テスト**

- 親子の検査(1段、同じプロジェクト、自分自身、子のあるTODOを子に、子を親に)。
- 親を閉じたときに子も閉じ、変更履歴が子ごとに1行ずつ残る。中止の理由が親と同じ。閉じた子はそのまま。親を再開しても子は閉じたまま。
- 木の並び: 並べ替えの種類ごと、絞り込みで子だけ当たるとき(つなぎの行)、タブの件数につなぎの行を数えないこと。ガントで完了の親を隠したときのつなぎの行。
- `due_after_parent`(同じ日は警告しない、閉じた子は警告しない)。
- 進み具合(中止を除く)。
- 日報の子の行の書き方。既定のテンプレートでフィクスチャと完全に一致したまま。
- 親を消すと子も消える。

完了条件: 上のテストが通り、`npm run test:perf` で一覧とガントが0.1秒以内。画面で、詳細パネルから子を足し、一覧とガントで親の下に字下げして出て、折りたためる。子が残っている親を完了にすると確認が出て、子も完了になる。子の日限注意がダッシュボードに「親 / 子」で出る。要件 S-1。

- ガントの矢印。座標の計算は `geometry.ts` の純粋関数にし、Vitest で確かめる。見えている行の範囲にかからない矢印は描かない。

**テスト**

## フェーズ23 週報

**Rust**

- 週報のテンプレート: `domain/report_template.rs` を週報の種類(`work`、`closed`、`waiting`、`next_week`、`attention`、`note`)と項目にも使える形に広げるか、週報用の型を足す(サブセッションが選び、報告する)。正規化・検査・所感の切り出しは日報と同じ規則で、同じ関数を使い回す。
- settings に `weekly_report_template` を足す。`update_settings` で検査し、エラーの文は日報と同じ書き方(節は既定の見出しで呼ぶ)。
- `DEFAULT_WEEKLY_REPORT_TEMPLATE` を tauri-specta の `constant` で `bindings.ts` に出す。
- 週報の組み立て(`domain/report.rs` か `domain/weekly_report.rs`): 設計書の節と書式のとおり。基準日は週の終わりと今日の早いほう。作業時間は、時間を入れたログだけを足す。
- `commands/reports.rs`: `kind: "weekly"` を受け付け、日付を月曜に寄せる。保存は `reports` の `weekly`(開始日は月曜、終了日は日曜)。.md の既定の名前は `週報_YYYY-MM-DD.md`。
- `tests/fixtures/weekly_report_2026-11-16.md`: 日報のテストと同じデータに、その週のほかの日の作業ログを足して作り、既定のテンプレートで完全一致を確かめる。

**画面**

- 日報の画面(`src/features/report/`)の上に「日報」「週報」の切り替え。週報では、前後のボタンが1週ずつ動き、「今週」で今週に戻り、見出しの横に週の範囲を出す。開いている種類は画面を移っても覚えておく(アプリを開いている間)。
- 設定画面の「週報のテンプレート」のカード(`ReportTemplateCard.tsx` を日報と週報の両方で使える形にする)。

**テスト**

- 週の境界: 月曜・日曜を選んだとき、年をまたぐ週(2026-12-28〜2027-01-03)。
- 基準日: 今週(今日まで)と過去の週(日曜まで)。待ちから、基準日より後に待ちに入ったものを除く。
- 今週完了・中止: 週の中で閉じて、今もその状態のものだけ。
- 今週の作業: TODOごとの作業日と合計、時間のないログ、本文を出す設定。
- テンプレートの項目のオン・オフ、並べ替え、見出しを変えたあとの再生成で所感が残ること。
- 既定のテンプレートでの週報のフィクスチャとの完全一致。日報のフィクスチャとの完全一致もそのまま。

完了条件: 上のテストが通る。画面で「週報」に切り替えると今週の週報が出て、前後の週に動け、所感を書いて再生成しても残る。コピーと .md の保存ができる。設定画面で週報のテンプレートを変えると再生成に反映される。要件 R-6。
