# 実装計画(v0.4.0)

v0.4.0 の4つの要件(表示倍率、C-3 バックアップの複製先、G-8 後続TODOのずらし、T-14 一括変更)を、フェーズ25〜30に分ける。順番は利用者と決めたもの。表示倍率を先にするのは、後のフェーズで足す画面(確認のダイアログ、一覧の操作の帯)を、初めから倍率をかけた幅で確かめられるようにするため。後続TODOのずらしを一括変更より先にするのは、複数のTODOの予定期間を1つのトランザクションで書く処理を、一括変更でも使うため。

仕様は `requirements-design.md` の「v0.4.0の詳細」にある。この計画は、フェーズごとの作業と完了条件だけを書く。フェーズ25(資料の詳細化)で、この計画と、設計書の v0.4.0 の記述を書いた。

ウィンドウを開かずにTODOを追加する機能(T-13)は、v0.4.0 の相談で将来に回した。相談で出た案と確かめることは、設計書の「v0.4.0の詳細」の「将来に回したもの」にある。

## 進め方

**体制(オーケストレーター方式)**

v0.3.0 と同じ。

- 作業場所は `dev-0.4.0` ブランチ。この資料の PR を main に取り込んでから、main から切る。リリースのタグ `v0.4.0` と同じ名前にしない(同じ名前のブランチとタグがあると、git の指定があいまいになるため)。
- 計画を持つセッション(オーケストレーター)はコードを書かない。フェーズごとにサブセッションを1つ立て、作業はサブセッションが行う。
- サブセッションは同時に1つだけ動かす。フェーズの間で同じファイル(`commands/mod.rs`、`commands/todos.rs`、`commands/settings.rs`、`repo/settings.rs`、`backup.rs`、`bindings.ts`、ガントのドラッグ、TODO一覧)を触るため。worktree は使わず、同じフォルダで作業する。

**サブセッションがすること**

- 最初に `CLAUDE.md`、この計画、設計書の該当する節を読む。
- そのフェーズだけを行う。設計にない判断が要るときは、進める前にオーケストレーターに聞く。
- 終わったら `npm run check` を通し、`dev-0.4.0` にコミットする。push はしない。
- フェーズの終わりに、次の3点を報告して止まる。
  - テストと型チェックの結果
  - 利用者に画面で確認してほしい操作の一覧(`npm run dev:sample` で起動して試す手順)
  - 設計書から変えた点
- フェーズで決まったファイルの場所や決めごとは、`CLAUDE.md` の「v0.4.0 の決めごと」に足す。

**オーケストレーターがすること(各フェーズの後)**

1. 差分を読み、`CLAUDE.md` の決めごと(層の分け方、コマンドの3か所、権限、文言)に合っているかを確かめる。
2. `npm run check` を自分でも通す。
3. 直す点があれば、同じサブセッションに頼む。
4. 結果と、確認してほしい操作を利用者に報告して止まる。
5. 利用者の「次へ」で、次のフェーズのサブセッションを立てる。

**そのほか**

- サブセッションからの質問は、この計画と設計書で答えられるものはオーケストレーターが答え、答えられないものは利用者に聞く。
- 次のことは、利用者に確認してから行う。
  - main への取り込み
  - 版の番号(`tauri.conf.json` の `version`)を 0.4.0 に上げること
  - push、タグ、リリース、ワークフローの実行
- 新しい画面と部品(表示倍率の選択、複製先のまとまり、ダッシュボードの知らせ、後続をずらす確認のダイアログ、一覧のチェックボックスと操作の帯、一括変更のダイアログ)はモックがない。Aizome の部品とトークンで既存の画面に合わせて作り、報告のときに見てもらう。
- 表示倍率は Windows で使うことが多いので、フェーズ26の画面の確認は、利用者に Windows でも見てもらう(Actions の `windows.yml` で作った実行ファイルを使う)。

**全フェーズで守ること**

- `npm run check`(型チェック、Rust の書式、Vitest、cargo test、clippy)を通す。日報と週報のフィクスチャとの完全一致のテストは、全フェーズで通ったままにする。
- コマンドを足すときは、`specta_builder()`、`build.rs` の `APP_COMMANDS`、`capabilities/default.json` の3か所をそろえ、件数のテスト(`commands/mod.rs`)も直す。v0.4.0 で足すコマンドは設計書のコマンド一覧にある7つだけ(41個から48個になる)。フェーズごとの件数は、26で41、27で44、28で46、29で48、30で48。
- 表は変えない(マイグレーションを足さない)。表を変えたくなったら、オーケストレーターに相談する。
- settings のキーは設計書と `CLAUDE.md` のとおりにする。読めない値は既定値として扱う。復元と取り込みで今の値を残すキー(`repo::settings::KEPT_ON_REPLACE`)を足したら、`CLAUDE.md` の「データの決めごと」の一覧も直す。
- 画面にプラグインの権限を足さない。フォルダとファイルのダイアログは Rust 側で開く。
- サンプルデータ(`sample.rs`)を変えるときは、モックと見比べる今の11件の表示(ダッシュボードの日限注意の件数と並び)を変えない。
- `perf.rs` に、各フェーズのコマンドの計測を足す。一覧とガントは0.1秒以内のまま。

## フェーズ26 表示倍率

設計書の「表示倍率」。

**Rust**

- 最初に、`set_zoom` を両方の OS で当て、並びが組み直されること(使える幅が減って折り返しが変わること)を確かめる。拡大鏡のように絵だけが大きくなるなら、進める前にオーケストレーターに相談する。
- settings に `zoom` を足す(読めない値と一覧にない値は `100`)。`SettingsInput.zoom` を足し、一覧にない値は「表示倍率は一覧から選んでください。」で断る。
- `update_settings` の `#[tauri::command]` の層で、メインのウィンドウの webview に `set_zoom` を当てる。起動時は、ウィンドウを出す前に当てる。
- `KEPT_ON_REPLACE` に `zoom` を足す(復元と JSON の取り込みで今の値を残す)。

**画面**

- 設定画面の「表示」のカードに「表示倍率」の選択(Aizome の `Select`)。選んだらすぐ保存して反映する(`useUpdateSettings`)。
- 150%・幅1280で6画面とダイアログが重ならずに使えるように、`src/styles/app.css` に幅で切り替える指定を足す。見直す所は設計書の「表示倍率」の「画面」にある。Aizome の写し(`tokens.css`、`aizome.css`)は書き換えない。
- 最小の960×600で150%でも、重ならず、横か縦にスクロールしてすべての操作に届くようにする。

**テスト**

- `zoom` の読み取り(既定値、一覧にない値、読めない値)と、`update_settings` の検査。
- 復元と JSON の取り込みで `zoom` が今の値のまま残る。

完了条件: 上のテストが通る。画面で、設定の「表示倍率」を変えるとすぐに画面全体の大きさが変わり、アプリを開き直しても同じ倍率で開く。70%〜150%のそれぞれで、ダッシュボード、TODO一覧と詳細パネル、ガント(ドラッグを含む)、日報、設定、起動時リマインド、各ダイアログを開き、重なりや届かない操作がない(幅1280と最小の960×600の両方。Windows でも)。非機能要件「操作性」の表示倍率。

## フェーズ27 バックアップの複製先

設計書の「バックアップの複製先(C-3)」。

**Rust**

- settings に `backup_mirror_dir` と `backup_mirror_last_ok` を足す。どちらも `update_settings` の入力には入れない(1キーずつ書く関数を `repo::settings` に足す)。`get_settings` の `Settings` には足す。`KEPT_ON_REPLACE` に2つとも足す。
- `backup.rs`
  - 複製先を `backups/` の毎日のバックアップ(新しい7個)にそろえる関数(`.part` に写してから名前を変える、残った `.part` を消す、複製先の `todo-YYYY-MM-DD.db` だけを7個に減らす、ほかのファイルには触れない)。
  - `restore` の中を、ファイルの場所を受け取る形に分ける(一覧から選ぶ復元と、ファイルを選ぶ復元で使う)。
- 起動時の `run_daily` のあとに複製する。常駐のタイマー(`notifier.rs`)は、複製先と `backup_mirror_last_ok` をメモリに持ち、最新の毎日のバックアップが複製先にそろっていなければ、起きるたびにやり直す。複製先を選んだ・やめた・復元したときは `Notifier::update` で入れ替える。動作ログは、失敗をその日の最初の1回だけ、また複製できたらそのことを1回書く(パスは書かない)。
- コマンドを足す(44個)
  - `choose_backup_mirror()`: フォルダのダイアログ(`spawn_blocking`)。データフォルダとその中は断る。選んだらすぐ複製し、成功したときだけ保存する。戻り値は `BackupMirror { dir, last_ok }` か `null`。
  - `clear_backup_mirror()`: 2つのキーを `null` にする。複製先のファイルは消さない。
  - `restore_backup_file()`: ファイルのダイアログ(`.db` の絞り込み)。選んだファイルを今の復元と同じ検査・マイグレーション・入れ替えに通す。戻り値はファイル名か `null`。復元のあとは `resident::apply`。
  - ダイアログを開く `#[tauri::command]` と、場所を受け取ってメモリ上の DB と作業用のフォルダでテストできる内側の関数に分ける。
- `Dashboard.backup_mirror_alert`(`{ last_ok, days }` か `null`)。判定は `domain/` の純粋関数(最後に複製できた日と、`backups/` の毎日のバックアップの日付の一覧を受け取る)。`get_dashboard` の中で `backups/` の一覧と settings から作る。
- エラーの文は設計書のとおり。

**画面**

- 設定画面の「データ」のカードに「バックアップの複製先」のまとまり(複製先がないとき・あるときの文とボタン、知らせの `Alert`)。
- 復元のダイアログ(`RestoreDialog`)に「ファイルを選んで復元」のボタン。復元したら、今の復元と同じくすべての一覧を取り直し、知らせの文を出す。
- ダッシュボードの一番上に、複製できない日が続いているときの `Alert`(warning)。
- フックは `queries.ts` に足す。複製先を選んだ・やめたら設定とダッシュボードを取り直す。

**テスト**

- そろえる関数(作業用のフォルダで): 複製先にないものだけを写す、複製先を7個に減らす、ほかの名前のファイルに触れない、残った `.part` を消す、`backup_mirror_last_ok` が最新の毎日のバックアップの日付になる。複製先がない・書けないときに失敗を返し、本体の `backups/` は変わらない。
- 知らせの判定: 複製先がない、最後に複製できた日より後のバックアップが2個(知らせない)・3個(知らせる)、最後に複製できた日が `null`。
- `choose_backup_mirror` の内側: データフォルダとその中を断る、複製に失敗したら保存しない。
- ファイルを選ぶ復元の内側: `backups/` の外のファイルから復元でき、退避が作られる。新しい版のもの、壊れたもの、Higiri の DB でないものは断り、データが変わらない。選んだファイルは変わらない。
- 復元と JSON の取り込みで、`backup_mirror_dir` と `backup_mirror_last_ok` が今の値のまま残る。

完了条件: 上のテストが通る。画面で、設定の「複製先を選ぶ」で別のフォルダを選ぶと、そこに毎日のバックアップが写る。複製先のフォルダを消す(か、外付けのドライブを外す)と、設定画面に知らせが出る(3日分は、`backups/` に日付を変えたファイルを置いて確かめる)。「ファイルを選んで復元」で複製先のファイルから復元できる。要件 C-3。

## フェーズ28 後続TODOのずらし

設計書の「後続TODOのずらし(G-8)」。

**Rust**

- `domain/shift.rs`: ずらす後続と日数を決める純粋関数。動かしたTODOのidと新しい予定期間、TODO の集まり、依存を受け取り、ずらす後続の一覧(id、今の予定期間、新しい予定期間)を依存の向きの順に返す。規則(足りない分だけ、いちばん遅い予定終了に合わせる、後続の後続、閉じた後続と予定開始のない後続は動かさずその先もたどらない、予定開始だけの後続、循環があっても止まる)は設計書のとおり。日数は暦日で、`domain/repeat.rs` の `shift` を使う。
- 予定期間を書いて変更履歴に `planned` の行を残す処理を、`update_todo` と同じ内側の書き方で、1つのトランザクションの中で複数のTODOに使える形にする(フェーズ29の一括変更でも使う)。
- コマンドを足す(46個)
  - `preview_dependent_shift(todo_id, planned_start, planned_end)`: ずらす後続の一覧(画面に名前を出すための項目つき。子は親のタイトル、プロジェクト名)。空なら確認は要らない。
  - `shift_with_dependents(todo_id, planned_start, planned_end)`: 1トランザクションで、計算し直してから、ドラッグしたTODOと後続の予定期間を書く。戻り値は動かしたTODOのidの一覧。
- `perf.rs`: 依存のつながった TODO(後続の後続まで続くもの)で、`preview_dependent_shift` を測る。

**画面**

- `useBarDrag.ts`: ドラッグを離して予定終了が後ろへ動いたら、`preview_dependent_shift` を呼ぶ。空なら今までどおり `useUpdateTodo` で保存する。空でなければ確認のダイアログを出し、開いている間はバーを離した位置で描く。
- 確認のダイアログ(題・文・一覧・3つのボタン。キャンセルと Esc はドラッグの取り消し)。日付の文は `rowLabel.ts` などに置き、Vitest で確かめる。
- フックは `queries.ts` に足し、`TODO_WRITES` の列に並べる。保存したら TODO の一覧とガントを取り直す。失敗したら、今のドラッグの失敗と同じく元の位置に戻して `Alert` を出す。

**テスト**

- ずらしの関数: ぶつからない(空)、1件を足りない分だけ、同じ日まで(同じ日は警告しない)、後続の後続(押されてぶつかるものだけ動く)、2件の先行TODOを待つ後続(いちばん遅い予定終了)、閉じた後続と予定開始のない後続(その先もたどらない)、予定開始だけの後続、別のプロジェクトの後続、動いていない先行TODOとの今の食い違いは直さない、循環のあるデータで止まる、月またぎ・年またぎ。
- `shift_with_dependents`: 予定期間と変更履歴(TODOごとに `planned` の1行)、`updated_at`、確認のあとに後続の予定が変わっていたときに計算し直すこと、予定期間の検査に通らないときに何も変えないこと。

完了条件: 上のテストが通る。画面で、ガントで先行TODOのバーを後ろへドラッグして後続とぶつかると確認が出て、「後続もずらす」で後続(とその後続)が足りない日数だけ動く。「このTODOだけ動かす」ではドラッグしたTODOだけが動き、「キャンセル」と Esc では元に戻る。余裕があってぶつからないときは何も聞かれない。要件 G-8。

## フェーズ29 一括変更

設計書の「一括変更(T-14)」。

**Rust**

- `domain/bulk.rs`: `BulkChange`(`set_due`、`shift_due`、`shift_planned`、`priority`、`status`)と、入力の検査、変えるもの・除くもの(理由の文)・ステータスのときの知らせ(`blocked`、`closing_children`、`next_rounds`)を決める純粋関数。今日の日付を引数で受け取り、ステータスは今の遷移の関数(`transition`)で確かめる。親と子を両方選んで閉じるときは、子を親と一緒に閉じるものとして数える。
- コマンドを足す(48個)
  - `preview_bulk_change(ids, change)`: `BulkPreview`。
  - `apply_bulk_change(ids, change)`: 1トランザクションで計算し直し、日限・予定・優先度は `update_todo` と同じ内側の書き方(フェーズ28で分けたもの)、ステータスは `change_status` と同じ内側の処理を1件ずつ(親を先に)。想定外の失敗は全体を断る。戻り値は `BulkResult { changed, skipped }`。
- `perf.rs`: 1,000件を選んだときの `preview_bulk_change`(0.1秒以内)と、`apply_bulk_change`(日限をずらす、ステータスを変える。1秒以内を目安。前後で元に戻して件数を変えない)を測る。

**画面**

- 選択の状態(選んだ id、Shift+クリックの起点)と、全部を選ぶ対象・範囲の選択・一覧に出なくなったものを外す計算は、純粋関数(`src/features/todos/selection.ts` など)にして Vitest で確かめる。見えている行だけを描く処理と折りたたみ(`tree.ts`)の後の行を使う。
- 一覧(`TodoTable.tsx`): チェックボックスの列と見出しのチェックボックス。表の DOM は変えず、セルの中に Aizome の `Checkbox` を置く。行のクリックとチェックボックスのクリックを分ける。
- 操作の帯と、4つのダイアログ(入力と確認の欄。入力を変えるたびに `preview_bulk_change` を引き直す)。保存の前に `saveOpenDrafts`。保存したら一覧の上に知らせ。文の組み立ては `bulkText.ts` などに置き、Vitest で確かめる。
- フックは `queries.ts` に足し、`TODO_WRITES` の列に並べる。保存したらプロジェクトと TODO の一覧を取り直す。

**テスト**

- 中身ごとの変更と除くもの: 閉じたTODOの日付、すでに同じ値、日限・予定期間がない、予定期間が片方だけ、行けないステータス(完了から未着手など)、実績期間が逆になる、閉じられない子のある親。
- 親と子を両方選んで閉じる(子は親と一緒に閉じ、二重に変えない)。子が残っている親だけを選んで閉じる(子も閉じる)。中止の理由が子にも入る。
- 繰り返しのあるTODOを閉じると次の回を作り、`next_rounds` に数える(終わりの日を過ぎるものは数えない)。
- 先行TODOが終わっていないTODOを作業中にするときの `blocked`。
- 入力の検査(日数の範囲、0、待ち、中止の理由)。
- 変更履歴: 日限と予定期間は1件ごとに1行、ステータスは今の `change_status` と同じ。
- 想定外の失敗で全体を断り、何も変わらない。
- 画面: 範囲の選択、全部を選ぶ対象(つなぎの行と折りたたんだ子を除き、描いていない行を含む)、絞り込みを変えたときに外れるもの。

完了条件: 上のテストが通り、`npm run test:perf` で一括変更の確認が0.1秒以内。画面で、一覧で複数のTODOを選び、日限をずらす・予定をずらす・優先度を変える・ステータスを変えるができる。変えられないものが混ざると、確認の欄に理由つきで出て、残りだけが変わる。先行TODOが終わっていないTODOを作業中にすると確認の欄に出る。子のある親を完了にすると子も完了になり、繰り返しのTODOは次の回ができる。要件 T-14。
